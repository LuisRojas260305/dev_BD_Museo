El proyecto

Un problema, la base de datos correcta para cada parte

El sistema gestiona usuarios, ventas y facturación con garantías transaccionales; un catálogo de obras heterogéneo; la auditoría de todo lo que ocurre; y recomendaciones basadas en relaciones. En lugar de forzar todo en un solo motor, cada necesidad vive donde rinde mejor. Un Backend gateway en Express orquesta los cuatro servicios.

Topología de la arquitectura

El frontend habla solo con el Backend gateway (puerto 3000). Este resuelve MySQL de forma directa y delega el resto en microservicios independientes, cada uno dueño de su motor. El aislamiento permite que un fallo en un servicio no tumbe a los demás.

MySQL · acceso directo mongodb-service cassandra-service neo4j-service
Persistencia políglota

Los cuatro motores

Cada base de datos entra por una razón concreta, no por moda. Relacional donde importan las transacciones; documental para lo heterogéneo; columnar para escribir mucho y siempre; grafo para las relaciones.

CP

MySQL / MariaDB

Relacional · vía XAMPP · :3306

El núcleo transaccional. Usuarios, ventas, facturas y multimedia, donde se necesitan garantías ACID y consistencia fuerte. El Backend lo consulta directo con el driver mysql2 y pool de conexiones.

MongoDB

Documental · mongodb-service :3001 · :27017

El catálogo de obras es heterogéneo: una pintura no tiene los mismos campos que una escultura. Se modela con discriminadores polimórficos de Mongoose (subtipos especializados por género) sobre una colección base. Paginación con $facet.

Fundamento teórico

Teorema CAP: dónde se para cada motor

Ninguna base distribuida ofrece a la vez consistencia, disponibilidad y tolerancia a particiones. La elección políglota se apoya justo en eso: cada motor sacrifica lo que su tarea puede permitirse perder.

CP

MySQL / MariaDB. Prioriza consistencia. Una venta o una factura no pueden quedar a medias: mejor rechazar que devolver un dato incorrecto.

CP

MongoDB. El catálogo se lee con consistencia; las escrituras del admin son puntuales y no requieren la disponibilidad extrema de un sistema de escritura masiva.

AP

Cassandra. La auditoría y las visitas nunca deben bloquear la operación. Se prioriza disponibilidad y se acepta consistencia eventual.

CA

Neo4j. El grafo de recomendaciones opera con consistencia fuerte sobre un único nodo; las relaciones deben ser exactas al recorrerlas.

Caso de uso

Una compra atraviesa las cuatro bases

El mismo evento de negocio toca cada motor según su fortaleza. El núcleo es transaccional y bloqueante; lo periférico se notifica en modo fire-and-forget, con consistencia eventual, para no frenar al usuario.

Reto de innovación

Dos capas de inteligencia sobre el grafo

Además de las recomendaciones, el proyecto suma inteligencia artificial en dos frentes que elevan la experiencia y cumplen el reto propuesto por la cátedra.

★ Reto +5%

Lenguaje natural → Cypher

Desde el panel de Neo4j se puede preguntar en español y el sistema traduce la pregunta a una consulta Cypher de solo lectura, con un motor de reglas y respaldo por IA. Valida que nunca escriba en el grafo.

"¿Qué obras de Pintura son las más compradas?"
→ MATCH (:Comprador)-[:COMPRÓ]→(o:Obra)-[:PERTENECE_A]→(:Genero {nombre:'Pintura'}) RETURN o ORDER BY ...
✦ IA generativa

Descripciones de obras con IA

Al abrir una obra con foto, si le falta una descripción de sala, se genera al vuelo una redacción curatorial breve a partir del título, el género, el artista y la época, y se guarda para no repetir la llamada. El administrador puede regenerarla.

"Mujer ante la ventana" · Pintura · Picasso
→ Una descripción evocadora, fiel a los datos, generada por el modelo.
